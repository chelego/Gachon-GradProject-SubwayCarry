# PassengerAI_V2 작업 지침

이 폴더와 하위 폴더를 수정하기 전에 반드시 다음 순서로 읽는다.

1. 저장소 루트의 `AGENTS.md`
2. 이 파일
3. `PASSENGER_AI_V2_GUIDE.md`
4. 변경 대상 코드와 Scene의 실제 연결 상태

현재 사용자의 직접 요청이 가장 높은 우선순위다. 문서와 코드가 다르면 임의로 구현을 확정하지 말고 차이를 먼저 보고한다.

## 구조 원칙

- V2는 `Perception -> Blackboard -> Journey Planner -> Utility Decision -> Action Executor -> Social Navigation -> Motor` 계층을 유지한다.
- 전체 여정의 순서와 실패 복구는 HTN 방식의 `Journey Planner`가 맡는다.
- Utility AI는 동일한 여정 단계 안에서 대기 위치, 좌석, 입석, 양보, 걷기와 달리기 같은 선택에만 사용한다.
- 개찰구, 계단, 열차 문, 좌석과 기대는 위치는 좌표가 아니라 용량, 방향, 예약과 입출구를 가진 Smart Object로 표현한다.
- 전역 경로 탐색과 근거리 군중 이동을 분리한다. A*는 선택된 목적지에만 사용하고, Social Navigation은 희망 속도를 안전한 실제 속도로 변환한다.
- V1 `UtilityJourney_AI` 코드는 비교 기준이다. 사용자가 명시적으로 요청하지 않는 한 V2 작업 중 V1 Scene과 코드를 재생성하거나 수정하지 않는다.

## 최적화 원칙

- 승객마다 모든 승객을 순회하거나 매 프레임 Scene 전체를 검색하지 않는다.
- 주변 승객 조회는 중앙 `CrowdManager`의 Spatial Hash 또는 동등한 공간 분할을 사용한다.
- 물리 이동만 FixedUpdate에서 처리하고 인식, 판단과 경로 계산은 서로 다른 저주기 스케줄로 분산한다.
- Hot Path에서 LINQ, 매 프레임 컬렉션 생성, 문자열 생성, `Find*` 호출과 반복적인 `GetComponent`를 사용하지 않는다.
- 경로 요청은 중앙 큐와 프레임 예산을 사용하고, 동일 목적지와 동일 장애물 버전의 결과는 재사용한다.
- 화면에서 멀거나 중요도가 낮은 승객은 인식과 판단 주기를 낮추되 여정 상태는 유지한다.
- 성능 개선을 주장하려면 Unity Profiler에서 CPU, GC Alloc, 경로 탐색 수, 주변 조회 수와 프레임 시간을 전후 비교한다.
- 승객 수 증가 실험은 행동 기준 변경과 분리한다. 먼저 기준 인원에서 행동을 통과시킨 뒤 스트레스 인원을 올린다.

## 구현 순서

1. 양방향 통로 교차
2. 같은 방향 군중 흐름과 속도 맞추기
3. 좁은 계단 합류
4. 개찰구 예약과 줄서기
5. 열차 문 하차 우선과 탑승
6. 객차 내 앉기, 서기와 기대기
7. 문 닫힘 임박 시 선택적 달리기
8. 전체 역간 여정 연결

앞 단계의 교착, 충돌과 성능 기준을 통과하기 전에는 다음 단계로 넘어가지 않는다.

## 검증과 보고

- 그래픽, 배치와 움직임의 자연스러움은 사용자가 직접 Play Mode에서 판단한다.
- 에이전트는 파일, 직렬화 데이터, 컴파일, Console, 테스트와 Profiler 수치만 검증 근거로 사용한다.
- 완료 보고에는 변경 파일, Scene 연결, 자동 검증, Profiler 측정 여부와 사용자가 확인해야 할 항목을 분리한다.
- 사용자 플레이 승인과 Git 업로드 승인은 구분한다. 사용자가 명시적으로 요청한 범위에서만 커밋·Push하며, 미검증 플레이를 완료로 보고하지 않는다.
